# Review: `wiki-loop` vs. WikiSkill (arXiv:2608.27454)

Reviewer pass over branch `wiki-loop` @ `14bb1f5`, 14 modules + 3 prompts under
`src/wiki_loop/`, against the paper (§3, Algorithm 1 / Appendix A, Appendix C) and
`docs/wiki-loop.md`.

---

## 1. Verdict

**Not a faithful implementation, and in its current state it cannot complete a single
loop.** The architecture is right — three layers, orchestrator-owned writes, patch-based
merges, a never-rolled-back wiki — and the hard parts (pipe-deadlock-free subprocess
harness, optimistic queue acks, atomic writes) are done carefully. But the delivery half
of the loop is dead code: **every proposal id generated by the proposer is rejected by
the proposal loader** (`prop_…` contains `_`, `is_valid_slug` forbids `_`), and even past
that, `apply` gates on a `gates["tier0"]` key that nothing ever writes. `validate` and
`apply` therefore fail 100% of the time, and neither has a test.

Separately, the **shipped default configuration is a no-op**: `run-maintainer` without
`--live` writes patterns to the staging wiki, while the proposer reads only the live wiki —
and the cron in `docs/wiki-loop.md:114` omits `--live`. Following the documentation
produces an empty live wiki forever.

Is it safe to run? Mostly, in the narrow sense that it cannot mutate `~/.agents/skills`
(apply is unreachable) and never writes to memex. It is **not safe for the wiki**: a
maintainer that re-emits `create` for an existing slug silently overwrites that page,
destroying accumulated corroboration — in a store whose entire premise is that it is never
rolled back. And malformed model output is silently indistinguishable from "nothing to
record", which permanently drops the traces that produced it.

On fidelity: the loop is **failure-only**. The paper's maintainer samples ~5 failing *and
~3 passing* traces and explicitly extracts successful strategies; this one discards any
session without a tool error. That is a substantive departure from §3.2.2 and it is not in
the design doc's list of deliberate divergences.

## 3. Findings

### A. Correctness bugs — the loop cannot complete

---

**F1 (P0). Every proposal id is rejected by the proposal loader. `validate` and `apply` are dead.**
`src/wiki_loop/gates.rs:45` · `src/wiki_loop/proposer.rs:152-156`

`Proposal::load` guards with `is_valid_slug(proposal_id)`, which permits only
`[a-z0-9-]` (`patterns.rs:485-493`). Proposal ids are minted as
`format!("prop_{:x}_{}", now_ms(), …)` — two underscores, always.

Verified mechanically:

```
generated proposal id = prop_19a7afd1e00_19a2f3c0de1122334455
Proposal::load accepts it? false
```

**Failure scenario:** the proposer runs, stages a perfectly good proposal, prints
`review with: memex wiki-loop validate prop_19a7…`. The operator pastes that exact
command and gets `invalid proposal id`. Same for `apply`. There is no id that both the
generator can produce and the loader will accept, so the human gate — the single most
important deliberate divergence in this design — is unreachable by construction.

**Why it survived:** `gates.rs` has no `#[cfg(test)]` module at all (`grep 'cfg(test)'
src/wiki_loop/*.rs` lists 10 of 14 files; `gates.rs` and `cli.rs` are absent). The entire
delivery path is untested.

Fix: give ids their own validator (allow `_`), or mint ids as kebab-case.

---

**F2 (P0). `apply` gates on a `tier0` key that is never written — it would bail even with F1 fixed.**
`src/wiki_loop/gates.rs:396-400` vs. `gates.rs:76-161`

```rust
let tier0 = proposal.gates.get("tier0");
match tier0 { Some(g) if g.passed => {} , _ => bail!("proposal has not passed Tier 0…") }
```

`tier0()` returns six individually-named gates — `secret_scan`, `name_slug`,
`scope_stamp`, `dedup`, `recently_rejected`, `referenced_paths` — and both callers insert
them under those names (`proposer.rs:201-204`, `cli.rs:408-416`). `grep -rn '"tier0"'`
returns exactly one hit: the read above. The key is never written by anyone.

**Failure scenario:** operator fixes F1, re-runs `apply`, and is told to
"run `wiki-loop validate` first" — which they just did, successfully. Unfalsifiable from
the CLI output: the proposal's own `proposal.json` shows every gate passing.

Fix: require all Tier-0 gate entries to pass (`gates.iter().filter(|(k,_)| k != "tier1")
.all(|(_,g)| g.passed)`), or synthesise a `tier0` aggregate when saving.

---

**F3 (P0). The documented default configuration is a no-op: maintainer writes staging, proposer reads live.**
`src/wiki_loop/cli.rs:228` · `src/wiki_loop/proposer.rs:48-56` · `docs/wiki-loop.md:114`

`execute_maintainer` writes to `cfg.wiki_dir(live)` — staging unless `--live`
(`config.rs:237-243`). The proposer reads `cfg.wiki_root` unconditionally, with no
staging option. The documented cron is:

```cron
*/30 * * * * /usr/local/bin/memex wiki-loop run-maintainer >> …
```

No `--live`. So patterns accumulate in `~/.local/state/wiki-loop/wiki-staging` while the
proposer reads `~/.memex/wiki`, which stays empty.

**Failure scenario:** operator follows the README exactly. For weeks, `run-maintainer`
reports `merged pattern … / created pattern …` and `run-proposer` reports
`wiki root … does not exist yet; run wiki-loop run-maintainer first` — or, once anything
else creates the dir, `no patterns with ≥2 corroborating sessions yet`. Both look like
healthy "nothing to do" output. `wiki-loop status` prints both counts side by side
(`cli.rs:467-471`) but nothing flags the split.

Compounding it: `append_skill_impact` always writes to `cfg.wiki_root` (`gates.rs:378-388`,
called with `&cfg.wiki_root` at `proposer.rs:239` and `gates.rs:438`), so the audit trail
lands in the live wiki while the patterns it references live in staging — split-brain even
in the mixed case.

Fix: the proposer must read the same wiki the maintainer wrote; thread `live` through, or
make staging→live an explicit promote step.

### B. Correctness bugs — silent data loss and wiki corruption

---

**F4 (P1). `create` silently clobbers an existing page with the same slug, destroying corroboration and `created`.**
`src/wiki_loop/patterns.rs:263-292`

```rust
let path = self.patterns_dir().join(format!("{}.md", scrubbed.slug));
self.write_atomic(&path, &content)?;   // unconditional overwrite, brand-new id
```

`create` never checks whether `{slug}.md` exists. The catalog is keyed by **id**
(`patterns.rs:237`), so a duplicate *slug* is invisible to every existing check. The new
page gets a fresh `generate_pattern_id()`, `created: now`, and only this run's evidence.

**Failure scenario:** iteration 1 creates `npm-peer-dep-resolution` with 4 corroborating
sessions across three weeks. In iteration 9 the catalog summary is long, or the model is
`gemini-3.8-flash` at `effort = "low"` (the shipped default, `config.rs:117`), and it emits
`action: "create"` with the same slug instead of `merge`. The 4-session page is replaced
by a 1-session page with a new id. The old id survives only as a dangling reference in
`logs.md` and in `purpose_patterns` of past proposals. Nothing logs a warning — `cli.rs:332`
prints `created pattern npm-peer-dep-resolution (pat_…)` exactly as it does for a genuine
first create.

This directly violates the module's own contract (`patterns.rs:1-3`: "The wiki is never
rolled back: edits only add, merge, or supersede") and the paper's compounding-knowledge
premise (§3.1: "accumulates and compiles knowledge continuously"). It is the single most
damaging bug here, because the wiki is the artifact the whole design says must never lose
state.

`quarantine()` has the identical collision at `patterns.rs:414`.

Fix: in `create`, if `{slug}.md` exists, either promote to a merge against the existing id
or bail. The brief's question — *can a slug/id mismatch fork a duplicate page?* — the
answer is worse than a fork: it is a silent replace.

---

**F5 (P1). Malformed model output is indistinguishable from "nothing to record", and permanently drops the traces.**
`src/wiki_loop/cli.rs:281-290` · `src/wiki_loop/harness.rs:158-169`

`MaintainerOutput` has `#[serde(default)]` on **both** fields:

```rust
struct MaintainerOutput { #[serde(default)] patterns: Vec<PatternOp>, #[serde(default)] summary: String }
```

`unwrap_envelope` falls back to returning the *envelope itself* when the `result` string
contains a `{` but nothing parseable (`harness.rs:162-168`). A claude/agy envelope like
`{"type":"result","result":"I couldn't find any clear patterns {see note}","is_error":false}`
therefore deserializes cleanly into `patterns: [], summary: ""`.

The run then takes the full success path: `append_log`, `update_index`,
`mark_processed(…, "ok", …)` and `ack_if_unchanged` for every session in the batch
(`cli.rs:364-383`), and `finish_run(run_id, "ok", …)`.

**Failure scenario:** the maintainer model degrades — a prompt-format change, a truncated
response, a rate-limit body, a model that wraps JSON in prose it also brace-quotes. Ten
sessions of real failures are acked off the queue, written into `processed` as `ok`, and
deleted. `is_processed` (`ledger.rs:88-97`) will skip them forever. `wiki-loop status`
shows `health: ok` and the circuit breaker never trips, because the run *succeeded*. The
only trace is a `logs.md` entry reading `- summary: (none)`.

This is the highest-value silent failure in the system: unrecoverable (raw traces stay on
disk, but the queue entry and the "not yet processed" bit are gone) and invisible.

Fix: make `patterns` a required field; treat a zero-op run with an empty summary as an
error, not an ack; and never ack a batch whose model call produced no structured output.

---

**F6 (P1). A lagging index yields zero records, which is read as "no errors" — the session is marked done and never compiled.**
`src/wiki_loop/cli.rs:205-216` · `src/wiki_loop/ingest.rs:114-136` · `src/index.rs:1296-1309`

`records_by_session_id` returns `Ok(vec![])` for a session that is not in the index — it is
a term query over the index, not a lookup that can fail:

```rust
let top_docs = searcher.search(&query, &TopDocs::with_limit(limit))?;   // empty ⇒ Ok(vec![])
```

`load_records` only falls back to the raw transcript on `Err` (`ingest.rs:117-132`), so an
empty result never triggers the fallback. Back in `execute_maintainer`:

```rust
let indices = digest::extract_error_turn_indices(&records);   // [] for []
if indices.is_empty() { ledger.mark_processed(…, "ok", &[])?; ack; continue; }
```

**Failure scenario:** the session is in `analytics.sqlite` (so `get_session_meta` succeeds
and the ingest-lag nack at `cli.rs:192` does *not* fire) but its turns have not yet been
committed to the tantivy index — a routine ordering, since the quiet window is 20 minutes
and index commits are batched. The session is acked, recorded `ok`, and `is_processed`
blocks it forever. This is precisely the outcome `docs/wiki-loop.md:123-125` promises
cannot happen ("partial traces are never compiled and then permanently skipped").

The same path makes a **partial** trace compilable: nothing compares `records.len()`
against `meta.message_count`, which the code already has in hand (`ingest.rs:24`). So the
brief's question — *can a session be compiled from a partial trace?* — yes: a half-indexed
session digests whatever turns exist and is then marked complete.

Fix: treat `records.is_empty()` (or `records.len() << meta.message_count`) as "not ready" —
nack for retry, or force the raw-transcript fallback.

---

**F7 (P1). `mark_processed` runs before `ack_if_unchanged`, so an entry updated mid-run is silently abandoned.**
`src/wiki_loop/cli.rs:364-383`

```rust
ledger.mark_processed(&entry.source, &entry.session_id, "ok", &contributed)?;
let acked = queue.ack_if_unchanged(entry, *fingerprint)?;
if !acked { eprintln!("note: … left queued for the next pass"); }
```

The message is wrong. On the next pass the entry *is* re-claimed, but the very first check
is `if ledger.is_processed(…) { ack; continue; }` (`cli.rs:183-186`) — and it was just
marked `ok`. So the entry is acked and discarded without ever being compiled.

**Failure scenario:** a session is resumed (`claude --resume`) while the maintainer is
running, or a hook fires a late turn event. `last_event_at` changes, the fingerprint
mismatches, the ack correctly refuses — and then the next run throws the work away anyway.
The new turns are never compiled. The optimistic-concurrency machinery in `queue.rs`
(which is otherwise well built) is defeated by the ordering of these two lines.

Related, same root cause: because `is_processed` is keyed on `(source, session_id)` and
`ended` is sticky (`queue.rs:99`), **any** resumed session is compiled at most once — the
turns after the first compile are permanently invisible.

Fix: swap the order — ack first, mark processed only if the ack succeeded.

---

**F8 (P1). Rollback at version 1 deletes a pre-existing, hand-authored skill directory.**
`src/wiki_loop/gates.rs:469-486`

```rust
let previous = if version > 1 { Some(read(backup v{version}.md)?) } else { None };
match previous { Some(c) => write(&skill_path, c)?, None => { let _ = std::fs::remove_dir_all(&skill_dir); } }
```

`apply` computes `version = latest_deployment_version().unwrap_or(0) + 1`
(`gates.rs:410-413`), which is 1 for a skill wiki-loop has never deployed — **including a
skill the user wrote by hand**. `apply` does back that content up to
`skills_backup/<name>/v1.md` (`gates.rs:416-420`), but rollback at v1 ignores the backup
and `remove_dir_all`s the whole directory.

**Failure scenario:** the operator has a hand-maintained `~/.agents/skills/deploy-runbook/`
with SKILL.md, scripts, and reference files. The proposer patches it, apply records v1,
the skill misbehaves, the operator runs `wiki-loop rollback deploy-runbook` expecting to get
their runbook back — and the directory, including every auxiliary file wiki-loop never
touched, is deleted. The SKILL.md body alone is recoverable from `v1.md`; anything else is
gone.

Fix: at v1, restore from `v{version}.md` when a backup exists and only remove the directory
when wiki-loop created it; never `remove_dir_all` a directory containing files wiki-loop
didn't write.

---

**F9 (P1). After any rollback, re-applying that skill fails forever on a primary-key collision.**
`src/wiki_loop/ledger.rs:244-267` · `src/wiki_loop/gates.rs:410-432`

`latest_deployment_version` filters `active_to IS NULL`; `retire_deployments` sets
`active_to` on **all** rows for the skill. The `deployment` table's primary key is
`(skill_id, version)` across all rows regardless of `active_to`.

So after a rollback: `MAX(version) WHERE active_to IS NULL` → `NULL` → `unwrap_or(0) + 1`
→ `1` → `INSERT … (skill_id, 1, …)` → **UNIQUE constraint violation** against the retired
v1 row.

**Failure scenario:** operator rolls back a bad skill, the proposer later produces a
corrected version, apply fails with a raw SQLite constraint error and never recovers — the
version counter can never advance past the retired rows. Every subsequent proposal for that
skill name is permanently unappliable.

Fix: compute the next version from `MAX(version)` over *all* rows for the skill.

### C. Paper-fidelity gaps

---

**F10 (P1, fidelity). The loop is failure-only: successful strategies are never compiled.**
`src/wiki_loop/cli.rs:212-216` · `src/wiki_loop/digest.rs:8-41` · `prompts/maintainer.md:10-16`

Paper §3.2.2: the maintainer "performs root cause analysis on the failing tasks, **and
extracts successful strategies from the passing tasks**." Appendix C pins the budget:
"up to 8 traces … a maximum of 5 failing traces … **and up to 3 passing traces** (to
identify effective strategies and prevent regressions in working behaviors)."

The implementation inverts this. `extract_error_turn_indices` returns `[]` for any session
without a tool-error marker, and such sessions are marked `ok` and dropped. The prompt
reinforces it — `maintainer.md:10` says "For each distinct **failure mode** in the digest",
and the only pattern shape offered is Symptom / Root Cause / Fix, which has no slot for a
working strategy.

**Consequence:** the wiki can only ever contain workarounds. Half the paper's knowledge
substrate, and the half responsible for "preventing regressions in working behaviors", is
absent. This is not in the design doc's four declared divergences (`docs/wiki-loop.md:36-52`) —
it is a silent departure.

---

**F11 (P1, fidelity). The maintainer never sees `W_{k-1}`, yet merges overwrite prior analysis.**
`src/wiki_loop/cli.rs:234-259` · `src/wiki_loop/patterns.rs:336-342`

The maintainer prompt gets a one-line-per-pattern catalog: `id | slug | title | scope |
status`. It never receives the Symptom / Root Cause / Fix bodies. Paper §3.2.2 is explicit:
"The Wiki Maintainer agent receives the **full wiki context** `W_{k−1}` alongside sampled
traces."

Now the merge path (`patterns.rs:336-342`) re-renders the page with
`scrubbed.symptom / root_cause / fix` — wholesale replacement of three sections by a model
that was never shown their prior contents.

**Answering the brief's question directly:** a merge *does* preserve corroboration,
`created`, identity, and prior evidence text (verified by the `create_then_merge_preserves_and_unions`
test, `patterns.rs:580-634`). It does **not** preserve the analysis. Nine iterations of
refined root-cause reasoning can be replaced by one terse restatement derived from a single
new session, and the diff is invisible — the test asserts the *new* fix text is present, not
that the old insight survived.

That is the opposite of "incremental, patch-based editing (e.g., appending, replacing, or
inserting text spans)" (§3.2.2). Feeding the page bodies into the prompt and asking for
span-level edits would fix both halves.

---

**F12 (P2, fidelity). The proposer is one-shot with no trace access, not the paper's ReAct agent.**
`src/wiki_loop/proposer.rs:107-132`

Paper §3.2.3: the proposer "operates in a multi-turn ReAct style", is given the index,
`skill-impact.md`, and an outcome summary, and "actively reasons and uses environment tools
(`read_file`) to select and inspect specific pattern pages **and raw execution traces**
`τᵢ ∈ T_train,k` on demand to diagnose root causes." Equation 3 makes `T_train,k` a formal
input.

Here it is a single stdin prompt with up to 10 pre-selected pattern pages
(`proposer.rs:59-91`) and **no trace access whatsoever**. The proposer cannot inspect the
evidence behind a pattern; it can only paraphrase the maintainer's summary of it. Combined
with F11 (the maintainer also never re-reads its own pages), no component in the pipeline
ever reads a pattern page's body and a raw trace together.

Legitimate as a cost/complexity tradeoff, but it is undocumented — `docs/wiki-loop.md`
claims only four divergences and this is not among them, while `docs/wiki-loop.md:29-31` and
`mod.rs:14-16` both describe the step in the paper's terms.

---

**F13 (P2, fidelity). Not every decision reaches `skill-impact.md`.**
`src/wiki_loop/cli.rs:444-452`

Paper §3.2.4: "Following **each** validation evaluation, the outer-loop orchestration harness
programmatically appends an entry to `wiki/skill-impact.md`". The auto-reject path
(`proposer.rs:237-250`), apply (`gates.rs:437-449`) and rollback (`gates.rs:489-497`) all do
this. `run_validate` does not — it writes `proposal.status` and the ledger row, and returns.

**Failure scenario:** a proposal passes gates at creation, the operator re-runs `validate`
(e.g. after the repo moved and `referenced_paths` now fails), and it flips to `rejected`.
Nothing records that in the audit trail the proposer actually reads. Eight days later the
`recently_rejected` backstop (7-day window, `gates.rs:140`) has expired and the proposer,
seeing no rejection in `skill-impact.md`, re-proposes the same intervention — the exact
failure mode the paper's tracker exists to prevent.

### D. Gating, concurrency, and robustness

---

**F14 (P2). Only the maintainer takes the role lock; the proposer and judge take none.**
`src/wiki_loop/cli.rs:124-130` vs. `cli.rs:78-83` · `docs/wiki-loop.md:118`

`run_maintainer` acquires `RoleLock`. `RunProposer`, `Validate`, `Apply` and `Rollback` all
run lock-free. The design doc states flatly: "A `flock`-based role lock makes overlapping
runs exit cleanly." That is true of one of five mutating commands.

**Failure scenario:** the `17 */6` proposer cron overruns (opus, a 20-minute timeout per
`config.rs:113`) and the next tick starts while the first is running — two proposals, two
`insert_proposal` rows, both bypassing the weekly ceiling check they each read before the
other wrote. Worse, a proposer can run *during* a maintainer pass and read `index.md`
between `write_atomic` of the patterns and `update_index` (`cli.rs:358-360`), i.e. a
catalog that disagrees with the pages on disk.

Fix: take a role lock in every mutating subcommand; consider a shared wiki lock so the
proposer cannot read mid-write.

---

**F15 (P2). Mixed-scope proposals become `global`, which bypasses both real gates.**
`src/wiki_loop/proposer.rs:96-105` · `gates.rs:203-215` · `gates.rs:285-290`

Scope is the shared scope of the motivating patterns, defaulting to `"global"` when they
disagree. Then:

- `referenced_paths` returns **`passed: true`** for global scope with the detail
  "global skill references paths (…) — verify manually" (`gates.rs:206-214`).
- `tier1` returns **`passed: true`** with "global scope: no project-specific replay set;
  skipped" (`gates.rs:286-289`).

So a proposal built from patterns spanning two projects — the case most likely to produce
an over-generalised, negative-transfer skill, which the paper warns about at length
(§4.2.2, "low-level workarounds … constrain stronger models") — is the case that gets the
*least* validation. `scope_stamp`, `dedup`, `name_slug` and `secret_scan` are all static and
trivially passed.

**Failure scenario:** two unrelated repos both hit npm peer-dep failures; patterns carry
`project:a` and `project:b`; the proposal is stamped `global`; it references
`scripts/fix-deps.sh` from repo A; both gates wave it through; it is now injected into every
session in every project. The brief asks whether an unvalidated proposal can reach `apply` —
this is the path (modulo F1/F2 currently blocking apply entirely).

Fix: a global-scope proposal should demand *more* evidence, not less — e.g. run tier1 against
the union of the contributing projects and fail closed on unresolvable path references.

**F16 (P2). Tier-1 trusts an unvalidated `assessments` array; one optimistic entry passes the gate.**
`src/wiki_loop/gates.rs:340-354`

```rust
let total = assessments.len();
let improved = assessments.iter().filter(|a| … == Some(true)).count();
let passed = total > 0 && improved * 2 > total;
```

Nothing checks that `total` matches the `used` sessions actually digested
(`gates.rs:302-319`), nor that each `session_id` corresponds to a real session, nor that
every digested session got an assessment.

**Failure scenario:** the judge — same one-shot harness, no schema (F17) — returns
`{"assessments":[{"session_id":"x","would_improve":true,"reason":"looks helpful"}]}` after
being shown five sessions. `1*2 > 1` → **pass**. A lazy or truncated judge response is
maximally permissive, which is backwards for a fail-closed gate. `prompts/judge.md` asks for
one entry per session but nothing enforces it.

Fix: require `total == used`, reconcile returned `session_id`s against the digested set, and
treat any missing assessment as `would_improve: false`.

**F17 (P2). The JSON-schema plumbing is dead code — no call site ever passes a schema.**
`src/wiki_loop/harness.rs:12-39` · call sites `cli.rs:275`, `proposer.rs:125`, `gates.rs:333`

All three pass `None` for `schema_path`, so the `role.json_schema` branch in `build_args`
can never fire. `config.rs:21-23` documents the flag, `RoleConfig::agy` sets
`json_schema: true` (`config.rs:41`), `docs/wiki-loop.md:100` advertises it, and
`defaults_are_self_consistent` asserts it (`config.rs:276`) — all inert.

This is the direct enabler of F5: the one mechanism that would force well-formed maintainer
output is configured, tested, documented, and never invoked.

**F18 (P2). Model-controlled frontmatter injection via unsanitised `title` and `scope`.**
`src/wiki_loop/patterns.rs:186-207`

```rust
out.push_str(&format!("title: \"{}\"\n", meta.title.replace('"', "'")));
out.push_str(&format!("scope: {}\n", meta.scope));
```

Quotes are escaped in `title`; **newlines are not**, in either field, and `scope` is
unquoted. `parse_frontmatter` terminates the block at the first `\n---` (`patterns.rs:89`)
and parses `key: value` per line.

**Failure scenario:** the maintainer emits `scope: "global\nstatus: active\nsuperseded_by: null"`,
or a title containing `\n---\n`. On the next `catalog()` read the injected keys win, or the
frontmatter boundary moves and the page's body is parsed as frontmatter. A pattern could
forge `status`, resurrect itself from `superseded`, or fabricate a `scrub_pass: v1` stamp.
Given the threat model in `docs/wiki-loop.md:47-48` ("A compromised maintainer cannot run
shell or touch the wiki"), the orchestrator should not be splicing raw model strings into a
structured header.

Related, lower: `apply_op` validates `op.slug` but builds the path from `scrubbed.slug`
(`patterns.rs:252` vs. `285`/`414`). They are equal today only because `scrub_op` happens not
to touch `slug` (`patterns.rs:526-546`). Validate the object you use.

**F19 (P2). Realistic secret shapes slip into the durable, indexed store.**
`src/wiki_loop/scrub.rs:14-81`

Misses that show up routinely in coding traces:

- **Stripe keys** — `sk_live_51H…`, `rk_live_…`, `whsec_…`. The `sk-` rule requires a
  **hyphen** (`scrub.rs:44`); Stripe uses an underscore. This repo ships a Stripe plugin, so
  these are plausible in its own traces.
- **Unquoted env assignments** — the rule requires quotes (`scrub.rs:73`), so
  `export API_KEY=abcdef123456` and `.env` lines without quotes pass through. This is the
  single most common shape in shell traces.
- **JWTs** — `eyJhbGciOi…`, ubiquitous in HTTP-debugging traces, no rule.
- **Connection strings** — `postgres://user:hunter2@host/db`, `mongodb+srv://…`, no rule.
- **AWS secret access keys** — the 40-char secret has no prefix; only `AKIA…` (the *public*
  id) is caught.
- **Slack webhooks** — `hooks.slack.com/services/T…/B…/…`, no rule.
- **`Authorization: Basic <base64>`** — only `Bearer` is handled.

Given `docs/wiki-loop.md:49-50` ("The wiki is durable and indexed; traces routinely carry
credentials"), the shortfall is material: a leaked value is written to a markdown store the
operator is encouraged to symlink into a memex memory root for indexing
(`docs/wiki-loop.md:130-132`).

Also note **scrubbing is post-hoc only**: `build_session_summary` (`digest.rs:51-110`) does
no redaction, so raw trace text — secrets included — is piped to the external maintainer,
proposer, and judge models. That may be intended (the model must see the failure), but it is
not stated anywhere, and the doc's framing implies scrubbing protects the data, when in fact
it only protects the file.

**F20 (P3). Subprocess timeout kills the child but not its process group.**
`src/wiki_loop/harness.rs:79-86`

`child.kill()` SIGKILLs only the direct child. `agy` and `claude` are wrappers that spawn
their own subprocesses; on a 20-minute timeout those grandchildren survive, holding memory
on a 16 GB swapless box. Pipe handling itself is done correctly — stdin and both output
streams are drained on threads (`harness.rs:61-72`), so the deadlock class the brief asks
about is genuinely closed.

Fix: `setsid` / `process_group(0)` and kill the group.

**F21 (P3). Run bookkeeping overstates success.**

- `written += 1` counts failed and quarantined ops (`cli.rs:348`), so `patterns_written` in
  `wiki-loop status` includes pattern ops that wrote nothing.
- A run where **every** op fails still reports `finish_run(…, "ok", …)` (`cli.rs:385`), so the
  3-strike circuit breaker (`cli.rs:136-145`) never trips on systematic write failures.
- Provenance is all-or-nothing: the `contributed` filter closure ignores its argument
  (`cli.rs:367-374`), so a session that evidences one pattern is credited with every pattern
  the run produced.
- `consecutive_failures` (`ledger.rs:174-190`) breaks on `"ok"` and counts `"error"`, but a
  crashed run leaves `"running"` forever — neither breaking nor counting, so a repeatedly
  crashing maintainer is invisible to the breaker.

- `extract_error_turn_indices` matches the bare substring `"error: "` against assistant prose
  as well as tool output (`digest.rs:15-28`), so ordinary discussion of an error selects turns.
  Over-selection only, but it inflates every digest.
- `build_session_summary` compares byte length against a char budget (`digest.rs:105`);
